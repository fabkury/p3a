# AGENTS.md

Guidance for AI coding agents working in this repository. This is the canonical
file: `CLAUDE.md` imports it, so project guidance goes here and only
Claude-specific notes go there. It is read at the start of every session, so
keep it accurate and keep it short.

## This branch is p3a 2.0 under construction

`v2` rebuilds p3a on a new architecture. Before doing anything here, read
`docs/2.0/README.md` and then `docs/2.0/PROGRESS.md`: they say where the work
stands, what comes next, and the rules of the work stream. Record progress
there as part of every step.

This file describes the tree as it is on `v2` today and changes in the same
commit as the tree. For 1.x (its architecture, release process and web UI
versioning) read `AGENTS.md` on `main`.

## Project overview

p3a is an ESP32-P4 Wi-Fi pixel art player. It plays WebP, GIF, PNG, APNG, JPEG,
and BMP files, animated and static: GIFs and stickers from Giphy and Klipy,
animated artworks from Makapix Club (a pixel art social network), static museum
artworks over IIIF and similar image CDNs, artworks fetched from a URL, and
local files on the SD card.

Target hardware is the Waveshare ESP32-P4-WIFI6-Touch-LCD-4B: 720x720 IPS
display (24-bit, MIPI-DSI), GT911 capacitive touch, 32 MB PSRAM, 32 MB flash,
and an ESP32-C6 Wi-Fi 6 co-processor reached through esp_hosted over SDIO.

The firmware is public (Apache 2.0). 1.x runs on real users' devices from
`main`; 2.0 has not shipped and runs only on the dev unit.

## Ground rules

- **Build, flash, and monitor whenever it helps.** Compiling to check a
  change, flashing the dev unit, and reading its serial log are ordinary parts
  of the work and need no permission. The dev unit is the board attached to
  the workstation by USB. It belongs to the development work: its flash, NVS,
  and SD card may be erased when the work calls for it. It is the only device
  you flash. Every other unit gets firmware through GitHub Releases, and the
  user cuts those.
- **Say what was tested.** A change that has not run on the device is
  unverified. Report how far each change got and name the tier
  (`docs/2.0/TESTING.md`): host tests, CI build, device tests, soak, manual.
  Do not describe untested work as done, working, or verified.
- **Clarifying questions are always welcome.** Ask when different readings of a
  request would lead to materially different work.

## Branches

- `main` is the 1.x line and is production. It takes critical fixes only. One
  more release is planned, 1.2.5. 2.0 work never touches `main`.
- `v2` is p3a 2.0, a clean break with no OTA path from 1.x (2.0 is installed

### Layers

2.0 components belong to layers, and a component may depend only on layers
below its own. Bottom to top: `util`, `board`, `storage`, `library`,
`sources`, `player`, `ui`, `net`, `main`. Every dependency is a `REQUIRES`.
`WHOLE_ARCHIVE`, `__attribute__((weak))`, and including a header from `main/`
or anything from `legacy/` are forbidden. What each layer holds is in
`docs/2.0/PLAN.md`.

### Conventions for 2.0 code

All in `components/p3a_util`; each header explains itself at the top.

- **Tasks** are created only with `p3a_task_create()` and a class
  (`RENDER`, `TOUCH`, `APP`, `NETWORK`, `BACKGROUND`). No literal
  priorities, no hand-rolled PSRAM stacks. Tasks are long-lived.
- **Never memory-map flash from a p3a task.** Every class except `RENDER`
  has its stack in PSRAM, the job runners included, and the IDF asserts
  when flash is mapped from such a task (`esp_partition_mmap`,
  `spi_flash_mmap`, and what uses them: the core-dump summary,
  `esp_image_verify`, and most of `esp_ota_*`). Ordinary reads and writes
  (`esp_partition_read`, `esp_ota_write`, NVS) are fine. Do mapping work
  from `app_main`'s task at boot, and guard it with
  `esp_ptr_external_ram()` on a local; later, hand the one call to
  `p3a_internal_call()`.
- **Run-once or slow work** is a job (`p3a_job_submit()`), never a task
  made for one call and never done on a task that must stay responsive.
- **Allocation** defaults to PSRAM through `psram_alloc.h`. Internal RAM is
  asked for explicitly, with the reason in a comment. No plain `malloc` in
  project code. cJSON allocates in PSRAM too (hooks set at the top of
  `app_main`): a parse tree is thousands of small allocations, which
  would otherwise drain the internal pool the Wi-Fi link and the SD card
  need.
- **Errors** that a caller must tell apart use `p3a_err.h`
  (`P3A_ERR_NOT_PLAYABLE`, `CORRUPT`, `MISSING`, `RATE_LIMITED`, `AUTH`,
  `NO_KEY`, `SD_FAILED`). Never classify a failure by matching a path or a
  message.
- **Events** (`p3a_event.h`) are for fan-out only. If the emitter knows who
  should act, it calls that code. New event types go in
  `p3a_event_types.h` with their meaning and payload.
- **Optional work** (a download, a refresh, a new TLS session) checks
  `p3a_mem_level()` before starting.
- **Files on the SD card** go through `components/p3a_storage`: paths are
  built by `sd_path` (never a literal `/sdcard/p3a`), writes go through
  `fs_atomic`, and binary files are `p3a_frame` containers with a schema
  number. A file that fails to load is never deleted. Once the card is handed to a computer (`p3a_storage_hand_over()`, by `p3a_usb`) writes are refused until the restart that ends every USB session. The card is formatted only by `p3a_storage_format()`, and only from the on-device flow a person confirms (`ui_card.c`). Free space is read
  from `p3a_storage_space()`, never computed in a request path. What may be
  assumed about FAT is stated in `p3a_storage.h`.
- **Artworks are `p3a_record_t` records in a `p3a_index_t`, and their bytes
  are blobs** (`components/p3a_library`). A source makes records with the
  `p3a_record_init_*` functions, hands finished downloads to
  `p3a_blob_adopt()`, and never builds a path under `blobs/` or deletes a
  file there itself.
- **A pin is a record in a pin list** (`p3a_pins.h`), never a copy of
  the bytes. The pin keeps its blob in the store: eviction asks
  `p3a_pins_keeps()` itself. A list plays as a channel of source
  `pinned`, and each record in it is still its own source's artwork.
  Code that changes a list goes through `p3a_pins_*`; who needs to know
  subscribes to `P3A_EVENT_PINS_CHANGED`.
- **Makapix is asked over HTTPS** (`makapix_rpc()`, D80): a channel's
  listing, a reaction, a playset. MQTT is for commands, presence and
  views. The player's key, token and certificates are never logged and
  never given out by the API. Everything Makapix does over time runs on
  its one task's tick (`makapix_register.c`); the MQTT client's own task
  only queues what arrives. A command becomes a call through
  `makapix_command_map()` (pure): add a command there, with its test.
- **A source with a mark to be credited with** ("Powered by GIPHY") gives
  it in its table (`credit`, and `credit_light` for light background
  colours), picture files compiled into its own component. The UI draws
  one in the band under the source's artworks (`ui_credit.c`, pure:
  which, where, and whether there is room).
- **A source that must know what is seen** (to count views) sets
  `shown` in its table; the scheduler calls it. Nothing else asks the
  renderer or the UI.
- **A source is a `p3a_source_ops_t` table** (`p3a_source.h`) registered at
  boot. Code outside a source never names one: it asks
  `p3a_source_get()` and calls through the table. Adding a source is adding
  a component in the `sources` layer and one registration in `app_main`.
- **A remote source is two files**: the requests (`source_giphy.c`) and
  what the answers mean (`giphy_parse.c`, pure). The museums are one
  source with a file per museum (`museum.h`): adding a museum is adding
  `museum_<id>.c` with its three functions and a row in the table. The pure file is tested
  on responses recorded from the service (`tests/assets/sources/`, with a
  second reading of them in `make_expected.py`) and on mutated copies.
  An address taken from a response is checked before it is fetched, and
  an API key goes into an address percent-encoded.
- **Logic is split from hardware** so it can be host-tested: the pure part
  in its own file with no IDF includes (`p3a_job_table.c`,
  `p3a_mem_pressure.c`), the thin device part beside it.
- **A restart used as a remedy** is counted through `p3a_recovery.h`, which
  bounds it. Never call `esp_restart()` on a failure without it.
- **The network is never waited for.** `p3a_net_start()` returns at once;
  code that needs the network subscribes to `P3A_EVENT_NET_UP` and
  `P3A_EVENT_NET_DOWN` or asks `p3a_net_is_up()`, and copes with "no".
  Anything that needs a real date asks `p3a_clock_is_set()` first.
- **Bytes from a file are untrusted.** A decoder or parser checks every
  size before computing with it (images: `ANIMATION_DECODER_MAX_DIMENSION`),
  refuses what is malformed with an error, and is tested on the corpus in
  `tests/assets/` against an independent implementation. p3a's own parsers
  also get a host test under the sanitizers on mutated input.
- **What reaches the panel goes through `display_renderer`**: a frame
  source for whole frames, an overlay for additions. Nothing else presents a
  framebuffer. Its timing code (from "Vsync setup" to the end of the
  consumer in `display_renderer.c`) is the result of the jitter work and is
  not edited without re-measuring against `docs/jitter/REPORT.md`.
- **Playing a file goes through `animation_player`**, which reports each
  request `ready`, `shown` or `failed`. Anything that must happen when an
  artwork is really on the panel (history, counting a view) hangs off
  `shown`, never off the request.
- **What plays next is the scheduler's** (`play_scheduler.h`). Nothing else
  asks the animation player for a file, apart from the test hooks. Its
  decisions are pure code with host tests (`sched_core.c` and
  `sched_pick.c`: which channel, which artwork; `sched_turn.c`: when to
  move on and what a failure leads to; `sched_history.c`; `playset.c`);
  change behaviour there, not in the wiring. A screen that covers the
  artwork stops the dwell timer with `play_scheduler_hold()`.
- **Channels are filled by the content task** (`sched_content.c`): it
  lists them, keeps their indices on the card, downloads their artworks
  and makes room, one transfer at a time. A source only lists
  (`ops->refresh`, into an empty index) and says where the bytes are
  (`ops->url`). When a channel is listed again and how long a failure
  waits is `sched_refresh.c`; which blobs go when the card fills is
  `p3a_evict.c`. Both are pure with host tests: change behaviour there.
- **A channel's size and refresh interval are asked through
  `sched_channel_capacity()` and `sched_channel_interval()`**, never
  from a source's table directly: a channel may set its own in a playset
  (D100). Its index file is one whichever playset plays it and keeps the
  deepest listing made; what is kept and what is read back is
  `p3a_index_shared.c` (pure, host-tested). A source that has the two
  settings gives their ranges in `channel_range`.
- **What is on the screen is the UI's model** (`components/p3a_ui`,
  `ui_model.c`, pure). Nothing switches screens: a screen or a notice is
  put up or taken down, and what is seen follows by precedence. Code
  outside the UI asks through `p3a_ui_hooks.h` (in `p3a_util`, callable
  from any layer), and only for what nothing but the caller knows; the UI
  finds out the rest by itself from events and the scheduler's state.
  Everything the UI draws goes through `ui_canvas_fill()` (which handles
  rotation and clipping) and `ui_font.h`; the look is `ui_style_default()`.
  `build-host/ui_preview` draws any screen on the workstation.
  What a gesture does on each screen is one function, `ui_route()`; add a
  behaviour there, with its host test, not in the touch task.
- **HTTP endpoints** are rows in a route table (`p3a_http.h`). A handler
  answers once through `p3a_http_ok`, `p3a_http_accepted` or
  `p3a_http_fail` and never writes an envelope, a status line or a header
  for them by hand. Everything is under `/api/v2/`. Anything slower than a
  few milliseconds is a job answered with 202. A new file of routes is a
  new table: check `MAX_TABLES` in `http_server.c`.
- **The web pages** are plain files under `components/p3a_net/static/`
  (no build step): `static/api.js` is the only place that calls the
  device, `static/ui.js` the shared chrome, `static/lib.js` everything
  that can be worked out without a browser, tested with node. A page's
  own rules live in its model file (`settings-model.js`,
  `playset-model.js`), which states no limit the firmware states: the
  settings come from the schema, and the tests read the rest out of the
  headers. A page never shows an artwork from its source: it uses the
  `file` address the device gives (D83).
- **The museum browser** (`static/museum/`) asks the museums from the
  browser, one adapter per museum. An adapter's id and axes are those of
  `museum_<id>.c` (`tests/web/test_museum.mjs` compares them): adding a
  museum is adding both. What adapters share is `request.js`.
- **HTTP requests go through `http_fetch`** (`components/p3a_fetch`), into
  memory, onto the card, or to a function as the body arrives (the
  firmware update). Nothing else opens an HTTP client. Its answers are `p3a_err.h`'s: act on `MISSING`,
  `RATE_LIMITED` and `AUTH`, never on a status number. It logs only a
  URL's host; do not log a URL elsewhere, because keys travel in them.
- **The firmware update** is `components/p3a_update`. Which release a
  device may install (`update_release.c`), when it looks and whether a
  new firmware has proved itself (`update_policy.c`) are pure with host
  tests: change behaviour there. A 2.x device installs only an asset
  named `p3a-v2.bin` (D85); never give another series that name.
- **Test hooks** live only in `components/p3a_test_hooks`, one command file
  per area, every symbol prefixed `p3a_test_`.
- **Managed components** are declared in the `idf_component.yml` of the
  component that needs them, pinned to exact versions. `dependencies.lock`
  is tracked. A version changes on purpose, in its own commit.
- **Long loops yield.** Console output is a busy wait, and the task
  watchdog reports a task that starves the idle task for 15 seconds.

### Moving code out of `legacy/`

Code leaves `legacy/` only inside a milestone: `git mv` it into the new tree,
strip its upward includes, check `docs/known-issues.md` for that file and
fix or re-record what it lists, and land it with tests at the tier the
milestone names. Deleting a legacy file without moving it goes in the
ledger's deletion log with the reason.

## Toolchain and environment

- ESP-IDF v5.5.4, target `esp32p4`, developed on Windows with PowerShell.
  Setting up a new machine: `docs/reference/esp-idf-5.5.4-setup.md`.
- Activate the IDF environment in the same command as the build:

  ```powershell
  $env:PYTHONUTF8 = "1"          # IDF's Python tooling raises Unicode errors on Windows without it
  . <IDF tools root>\Microsoft.v5.5.4.PowerShell_profile.ps1   # EIM install; commonly C:\Espressif\tools\
  $env:ESP_IDF_VERSION = "5.5"   # REQUIRED after activation, see next bullet
  ```

- **`ESP_IDF_VERSION` must be `5.5`, not `5.5.4`.** EIM 0.13.x's profile
  exports the full version, but official IDF 5.5.x activation exports
  major.minor, and `esp_wifi_remote`'s Kconfig keys its version fragments on
  that convention. With the wrong value the fragment silently loads nothing,
  `sdkconfig` is generated with esp_hosted on SPI and an "invalid" slave
  target, and the build dies with `#error "Unknown Slave Target"` deep inside
  esp_hosted. The lab and CI set it; raw `idf.py` needs it set by hand.
  `tools/compare_sdkconfig.py` catches the result as dozens of unexpected
  differences. Recovery: delete `sdkconfig` and `build/`, set the variable,
  rebuild.
- **Silicon revision guard.** The board's ESP32-P4 is silicon rev v1.0.
  `CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y` and `CONFIG_ESP32P4_REV_MIN_1=y` in
  `sdkconfig.defaults` must never be removed, and the generated `sdkconfig`
  must show `CONFIG_ESP32P4_REV_MIN_FULL=1`: from IDF 5.5.2 the default is
  rev 3.01 only, and the bootloader rejects such images on this board.
- **`sdkconfig.defaults` is edited, `sdkconfig` is not.** Defaults apply only
  when `sdkconfig` is created, so delete `sdkconfig` after editing the
  defaults file. A setting changed through `menuconfig` is lost unless it is
  copied into `sdkconfig.defaults`. Options for components that 2.0 has not
  brought in yet are parked, commented, at the bottom of the file under the
  milestone that enables them.
- **Run `idf.py` from the repository root**, with the directory change in the
  same command. `idf.py` treats the current directory as the project; run from
  inside a component it configures that component as a standalone project and
  leaves a stray `build/` directory there.
- The repository is also reachable through a second path on this workstation
  (`C:\Users\fab\F\...`). A build directory configured through one path
  refuses the other; always use the Dropbox path.
- The dev unit, its serial port, the secrets file and the 1.x flash backup
  are described in `docs/2.0/README.md` under "Environment".

## Build commands

```powershell
python host/p3a-lab/lab.py build release   # or: build test. Builds and runs the build checks
python host/p3a-lab/lab.py up              # test build, flash, wait for the console
python host/p3a-lab/lab.py provision       # name the dev unit and put it on the test rig's Wi-Fi
python -m pytest tests/device              # flash the test build, run every device test (18 minutes)
python -m pytest tests/device/test_smoke.py tests/device/test_<area>.py   # a checkpoint
cmake -S tests/host -B build-host -G Ninja; cmake --build build-host; ctest --test-dir build-host --output-on-failure
node --test tests/web/*.mjs                # the web pages' shared logic (PowerShell: name the files)
python tools/check_tree.py                 # layer rule and forbidden patterns

Set-Location <repo root>                   # raw idf.py: in the same command, every time
idf.py build
idf.py -p COM5 flash
idf.py fullclean
```

- Build output goes to `build/`. Overlay builds (test, trace, diag) go to
  `build-<name>/` and never touch the default configuration.
- `idf.py` refuses to run under an MSYS environment (Git Bash) and still
  exits 0. Run it from PowerShell, or through the lab, which strips the
  `MSYSTEM` variables.
- Before a checkpoint: the tree checks, the host tests, the test build, and
  on the device the smoke set plus the tests of the area changed. The whole
  device suite and the release and trace builds run at the end of each
  milestone. CI runs on every push and is not waited for: read its result
  before the next commit. Do not wait idle on a long run; read and write
  the next step meanwhile. The full table and how deep tests should go are
  in `docs/2.0/TESTING.md` under "What runs when".
- **Before pushing a new host-tested file, build the host tests in WSL
  too**: `wsl -e bash -lc 'cd /mnt/c/<repo> && cmake -S tests/host -B
  ~/p3a-host -G Ninja -DP3A_SANITIZE=ON && cmake --build ~/p3a-host &&
  ctest --test-dir ~/p3a-host'`. CI compiles them with Linux gcc under the
  sanitizers, and MinGW's headers pull in more than gcc's: a missing
  `<stddef.h>` passes on the workstation and fails there.
- **A dependency change needs a from-scratch configure in the CI container**
  before it is pushed. The workstation keeps downloaded components and a
  resolver cache, so it can pass where a clean machine fails. Docker runs
  inside WSL; clone into the WSL home (not `/tmp`, not `/mnt/c`) and run:

  ```bash
  git clone -q --branch v2 --depth 1 file:///mnt/c/<repo> ~/p3a-ci && cd ~/p3a-ci
  docker run --rm -v ~/p3a-ci:/work -w /work espressif/idf:v5.5.4 bash -c     'git config --global --add safe.directory /work; . $IDF_PATH/export.sh; export ESP_IDF_VERSION=5.5; idf.py reconfigure'
  ```

  One "Missing kconfig option. Re-run the build process..." warning is
  normal; the error "after retry" is not. The container leaves root-owned
  files: delete `~/p3a-ci` from inside a container.
- `idf.py monitor` and .NET `SerialPort` reset the board when they open the
  port. To read the log without a reset, open the port with DTR and RTS held
  low (pyserial: set `dtr = False` and `rts = False` before `open()`); a short
  RTS pulse then resets the board on purpose.

## Configuration and versioning

- One version number, `PROJECT_VER` at the top of the root `CMakeLists.txt`.
  It is `2.0.0-dev` until the release commit. There is no separate web UI or
  API version in 2.0.
- Where a value lives (`docs/2.0/DECISIONS.md` D32):
  - **Kconfig** holds the shape of the build only.
  - **`components/p3a_settings/settings.json`** holds everything a user may
    change. Adding a setting is one entry there; the build generates the C
    table and the typed struct (`tools/gen_settings.py`), and the store
    validates, saves and reports changes with no further code. Read settings
    with `p3a_settings_get()`. Never add an NVS key or a Kconfig default for
    something a user sets.
  - **`p3a_limits.h`** holds constants nobody changes.
  - **A component's own storage** holds device state (a registration, an
    id, a counter). Wi-Fi and Makapix secrets keep their own NVS namespaces.
  - An API key is never compiled into a binary, and a setting flagged
    `secret` is never logged.

### Keeping documentation honest

- **When you fix a stale fact, sweep for it.** A wrong claim rarely lives in
  one place. Fix every copy together, with a commit message that states the
  current behavior.
- The ledger is updated in the same commit as the work it describes.
- Agent guidance belongs in this file. `CLAUDE.md` stays a thin import plus
  Claude-specific notes.

## Releases

The user cuts releases. 2.x has no release process yet; it is defined at
M5.3. Two facts are already fixed: 2.x firmware ships under a new asset name
so that 1.x units never see it (`docs/2.0/DECISIONS.md` D12), and nothing
installs on a device without its owner's approval. The 1.x release process is
in `AGENTS.md` on `main`.
