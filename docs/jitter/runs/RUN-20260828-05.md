# RUN-20260828-05 — 11 min with SD/flash/verify marks (ring overflowed; probes reworked)

- Diag build ade63f5c, "Work mix", 14:25–14:37 local. 9296 frames captured but
  the 8192-entry ring overflowed between 20 s pulls (sd_read marks at ~70/s):
  38 k of 121 k entries lost. Fixed for RUN-06: 32768-entry ring and one
  span entry per SD/flash op (duration carried in `lateness_us`).
- In-scope stalls: 7 (all with an `sd_write` in the window), warns 10.
  Producer anomalies: 83 (82 upscale-dominated). Lift vs base rate:
  sd_read 2.3x, loader_load 1.8x, sd_write 1.5x, download 0.7x.
- **SD write performance is terrible**: 2329 writes of 32 KB (the http_fetch
  chunk, allocated in PSRAM) took median 72 ms, p90 187 ms, p99 345 ms,
  max 407 ms (≈ 450 KB/s median, 175 KB/s p90); 532 writes > 100 ms. That is
  sector-by-sector pace, not multi-block. UART earlier showed
  `fs_atomic: Rename failed` / `sd_health: SD write failure`.
- SD reads: 35 k, median 307 us for 512 B (directory/stat traffic), one 72 ms.
- Flash: 375 ops in 11 min, all 32-byte reads (NVS entry reads), median
  111 us, one 47 ms outlier. Not a stall driver (H1 further weakened).
- Working hypothesis (H3/H4 merged): SD write DMA from a PSRAM buffer while the
  card is slow/busy degrades PSRAM/cache throughput for both cores, inflating
  the CPU upscale 5–12x for a frame. To be tested in Phase 4 with the moving-bar
  animation: `sd` provoke with PSRAM vs internal buffers and 512 B vs 32 KB
  chunks, plus a read-storm variant.
